T-G6  WINNER SHAPE — aggregate first, attach the wide profile after
      MATCH (a)-[:FOLLOWS]->(b)-[:RECOMMENDS]->(c),(a)-[:VISITS]->(c)
      WHERE a.kind='person'

      MATCH (p:`PROFILE`)-[:PROFILE_OF]->(c)
      RETURN c.title AS venue, reach, <200 p.* cols>

      Also: gem compile 12,292 ms (default planner 840 ms) — see COMPILE below.

COMPILE — a real (documented, not worked around) planner defect
     Same query, same workspace, 200 RETURN columns:
       single-MATCH form, -j gem                          685 ms
       WITH form, default planner (rung0/rung1)           816-840 ms
       WITH form, -j gem                              9,000-12,300 ms
       WITH form, -j gem TLX_GEM_NOSPLIT=1                8,330 ms
       WITH form, -j gem TLX_GEM_ONLY_UNION=1            11,702 ms
     So it is NOT the UnionAll split enumeration: GEM's join-order search on a
     MULTI-PART query is ~12x more expensive and scales linearly in the number of
     projected columns (~48 ms/col).  Consistent with L-T23's earlier finding that
     "a later query part embeds the previous part's un-expanded NAry join".
     Fixing it would also unlock lever L-A (a genuinely 1000-column profile card).
