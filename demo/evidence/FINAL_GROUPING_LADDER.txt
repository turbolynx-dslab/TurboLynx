WHY THIS EXISTS (tslee's objection, restated)
  The paper calls the workload a grouping/analytical query; the v6 hero returns 200 raw
  profile columns per row.  Naively adding GROUP BY collapses the result and SSRF loses
  the material it compresses.  That objection is REAL and reproducible: see
  g/SHAPE_TRIALS.txt T-G1/T-G2/T-G3/T-G5 — every shape that puts the aggregation ABOVE
  the wide profile seek kills the SSRF rung outright (+4.1% / +0.9% / -3.5% / +25.3%).
  The fix is structural: aggregate FIRST, materialize the wide heterogeneous profile
  AFTER the collapse, and give the post-collapse attach enough rows to matter.

== THE ONE QUERY (identical text on every rung; only env/planner flags change) ==
  MATCH (a:`NODE`)-[:FOLLOWS]->(b:`NODE`)-[:RECOMMENDS]->(c:`NODE`),
        (a)-[:VISITS]->(c)
  WHERE a.kind = 'person'            -- SI-off rungs use: a.kind IS NOT NULL
  WITH  c, count(*) AS reach                          <-- GROUP BY venue
  MATCH (p:`PROFILE`)-[:PROFILE_OF]->(c)
  RETURN c.title AS venue, reach, <200 p.* cols>;
  ("for every venue, how many follow -> recommend -> visit paths reach it, and its
    full profile card")
  200 profile cols = /data/ladder-v7-src/profile_cols.txt (40 categories x 5 props,
  disjoint; identical text to v6's).

  Cardinalities — this is the point:
    172,000  traversal rows entering the aggregation
     33,452  groups out of the GROUP BY            (5.14x collapse — a real grouping)
    167,260  wide result rows (33,452 venues x 5 profile records each)
        202  columns per row, 5 non-NULL of the 200 profile columns (97.5% NULL)

Toggle mapping (cumulative, unchanged from the v6 ladder):
  SI   : predicate form  IS NOT NULL -> = 'person'   (converter graphlet prune)
  GEM  : -j gem  TLX_DIVERGE_ORDER=1 TLX_GEM_SPLIT_TARGET=a

== THE STRUCTURAL RULE (why this shape and not the obvious ones) ==
The binder desugars every property of a WITH-visible variable that is projected after
the aggregation into a `first(...)` AGGREGATE — so the wide seek is pulled back below
the HashAgg and the row format is re-flattened by 200 aggregate reads.  Evidence:
  `WITH c, p, count(*) AS reach RETURN c.title, reach, <200 p.* cols>`  (T-G7)
     -> 462 CScalarAggFunc(first) in the plan, gem 1364.5 -> ssrf 1305.0 = -4.3%
  `WITH c, count(*) AS reach  MATCH (p)-[:PROFILE_OF]->(c)  RETURN ...`  (T-G6, ours)
     ->   3 CScalarAggFunc(first) + 3 count_star, wide seek strictly above the agg
DEFERRAL THEREFORE REQUIRES the wide variable to be UNBOUND in the aggregating part,
i.e. introduced by a second MATCH after the WITH.  Everything else in the search space
(200 max(), 200 count(), 200 group keys, DISTINCT) lands on the wrong side.  Full trial
log with numbers: g/SHAPE_TRIALS.txt.

== COMPILE — FIXED 2026-08-28.  Was the one real cost of this shape ==
  ROOT CAUSE (measured, not assumed).  The standing hypothesis was that
  CJoinOrderGEM::DCost -> DeriveStats derived full column statistics for all 200
  projected columns per candidate join because it passes NULL required-relational
  properties.  That is REFUTED: a NULL prprel makes CExpressionHandle::DeriveStats
  build an EMPTY required-stat-column set, so the 200 columns land in pcrsWidth
  (width only, no histograms) and a restricted column set would not shrink that.
  Instrumenting the xform showed where the time really went:

    cols  compile   GEM PexprExpand   DeriveStats in GEM   rest of the optimizer
      10  2056 ms    558 ms (2308x)    287 ms (64054 calls)   1498 ms
      50  3012 ms   1020 ms (2308x)    747 ms (64054 calls)   1993 ms
     100  4234 ms   1506 ms (2308x)   1043 ms (64054 calls)   2728 ms
     200  6890 ms   2460 ms (2308x)   1770 ms (64054 calls)   4430 ms

  The call COUNT is constant; only the per-call width grows with the projection.
  DeriveStats was 26% of compile — not the 8 s.  The multiplier was that
  PexprExpand ran 2,308 times, and 2,305 of those were bit-identical: the same
  memo group (475) with the same child groups (404, 411, 471).  Cause: the xform
  pattern is CLogicalNAryJoin(CPatternMultiTree, CPatternTree), and CPatternMultiTree
  binds concrete alternative TREES, so on a multi-part query the pattern re-fires
  once per alternative of the previous part's join — and the memo then discards
  every repeat as a duplicate.  The sibling expansions that share this pattern
  (MinCard, Greedy) already stop after one binding; GEM never did.

  THE FIX (2 files, engine):
   1. CXformExpandNAryJoinGEM::Transform declines a binding whose relational
      children still contain an un-expanded CLogicalNAryJoin.  That binding is
      the FIRST one, and it is not merely redundant but WRONG: GEM walks into the
      NAry child to find the split target's table, picks a table this join never
      asked to split on, and the UnionAll it builds does not partition the input
      (215,000 rows instead of 167,260).  Today's build only gets the right answer
      because cost-based search prefers one of the 2,304 other alternatives.
   2. CXformUtils::FApplyToNextBinding lists ExfExpandNAryJoinGEM as apply-once,
      so the binding loop stops at the first binding that yields a result.  (Not
      CXform::IsApplyOnce, which breaks after binding 1 whether or not it produced
      anything — that would keep exactly the degenerate binding above.)
  Net: 2,308 expansions -> 2 (the triangle and the profile attach), one each.

  AFTER:  rung0 / rung1 (default planner) : 449.7 / 447.3 ms
          rung2 / rung3 (-j gem)          : 366.9 / 367.1 ms
  GEM now plans FASTER than the default planner on the same query; the compile
  defect and its ~48 ms-per-projected-column scaling are gone.  Nothing about the
  plan changed — see RESULTS IDENTITY and EVIDENCE below, all re-run and unchanged
  (md5 af57c00c…, peaks 65,751,448 / 27,466,010 / 167,260 / 167,260, 0 HashJoin,
  26 CPhysicalInnerIndexNLJoin, B0/B1 opposite orders at cost 263888.889).

== PACING — a booth click, measured through the page ==
The server used to time with `-i 1 --warmup`, which plans AND executes the query
twice, in a fresh process, per click.  Removing --warmup is NOT an option and the
numbers say why: the engine's first execution in a process pays a per-process load
of ~4.0-6.5 s WHATEVER the rung, so a one-shot `-i 1` reports a cold number and
flattens the ladder outright (measured, 5 reps interleaved):
    -i 1          rung0 6540.2  rung1 4531.0  rung2 4585.9  rung3 3977.0 ms
                  i.e. rung2 is SLOWER than rung1 — the ladder is destroyed.
    -i 1 --warmup rung0 3201.2  rung1 1856.8  rung2  612.8  rung3  299.2 ms
So server.py now holds ONE long-lived engine process per mode (EngineSession) and
pays that cold load once, at server start.  A click is then one compile + one warm
execution of the real query — nothing cached, nothing replayed — and reports the
same measurement the certified protocol does (a warm session read 365.8 ms compile
/ 300.9 ms execute against bench medians of 367.1 / 299.2).

  click wall clock, 5-cycle soak through /api/run (medians):
    base 3.94 s   si 2.31 s   gem 1.04 s   ssrf 0.78 s
    (was 13.9 / 10.2 / 25.2 / 24.7 s)
  and wall == compile + execute + ~25 ms of HTTP on every rung.
