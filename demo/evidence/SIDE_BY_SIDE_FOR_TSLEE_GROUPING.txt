  MATCH (a:`NODE`)-[:FOLLOWS]->(b:`NODE`)-[:RECOMMENDS]->(c:`NODE`),
        (a)-[:VISITS]->(c)
  WHERE a.kind = 'person'            -- SI-off rungs: a.kind IS NOT NULL

=====================================================================================
A. WHY THE OBVIOUS GROUPING SHAPES DESTROY THE SSRF RUNG (the objection, measured)
=====================================================================================
All on /data/ladder-v6-ws, interleaved in one sweep, gem -> ssrf, median of 3-4.
(These are the LOADED-session numbers and stay as they were: each row is a
gem-vs-ssrf ratio measured inside its own interleaved sweep, so the verdicts are
load-neutral — which is the whole point of the table.)
  control  RETURN a.name, b.title, c.title, <200 p.*>        890.9 -> 434.8   -51.2%
  200 x max(p.*)      + count(*), GROUP BY venue           1246.2 -> 1297.3    +4.1%
  200 group keys      + count(*)                           1256.5 -> 1268.0    +0.9%
  200 x count(p.*)    + count(*)                            835.3 ->  806.0    -3.5%
  DISTINCT over 201 columns                                1334.9 -> 1671.7   +25.3%
The IdSeek still picks the row format in every one of them (fmt=ROW 107 chunks,
20.96M nulls — bit-identical to the control).  What kills the rung is the operator
ABOVE it: the HashAgg reads all 200 columns per input row and re-pays exactly the
padding SSRF avoided.  Cost split against the control: the aggregation adds +355 ms
on columnar input but +862 ms on row-format input.  So it is NOT "the result set got
too small" — it is the aggregate re-flattening the row format.

=====================================================================================
B. THE STRUCTURAL RULE THAT FIXES IT
=====================================================================================
The binder turns every property of a WITH-visible variable that is projected AFTER the
aggregation into a `first(...)` AGGREGATE, which drags the wide seek back below the
HashAgg.  Plan-node counts, same query text apart from where `p` is bound:
  WITH c, p, count(*) AS reach RETURN c.title, reach, <200 p.*>
      -> 462 CScalarAggFunc(first)   gem 1364.5 -> ssrf 1305.0   -4.3%   FAIL
  WITH c, count(*) AS reach  MATCH (p:`PROFILE`)-[:PROFILE_OF]->(c)  RETURN ...
      ->   3 CScalarAggFunc(first) + 3 count_star                        WINNER
=> the wide variable must be UNBOUND in the aggregating part, i.e. introduced by a
second MATCH after the WITH.  That is the only shape in the search space that puts the
GROUP BY strictly below the wide materialization.

G. TWO THINGS THAT GOT WORSE, STATED PLAINLY
=====================================================================================
G1 COMPILE.  rung2/rung3 spend 8.0 s in the planner on a quiet machine — 14.6x
   rung0/rung1's 0.54-0.55 s, and the quiet re-measurement did NOT soften it.
   Isolated on v6: single-MATCH + gem 685 ms; WITH + default planner 816-840 ms;
   WITH + gem 9,000-12,300 ms.  It is not the UnionAll split (TLX_GEM_NOSPLIT still
   8,330 ms) and it scales ~48 ms per projected column (10/50/200 cols =
   3.2/4.5/12.3 s).  GEM's join-order search on a multi-part query is the cost — the
   same "a later query part embeds the previous part's un-expanded NAry join" that
   caused the DCost overflow fixed earlier.  Consequence: the alternative fix for the
   SSRF rung (widening the profile union to 800-1000 columns) is priced out at
   ~40 s/click.  For the booth-click cost see G1b — it is ~25 s, not the ~10 s an
   earlier draft estimated, because the compile is paid twice.
   This is the highest-value follow-up fix.

   G1b NEW, and it doubles the booth cost: the certification protocol
   `-i 1 --warmup` PLANS TWICE — once for the warmup pass, once for the timed
   one.  Verified directly on the rung-3 config, same query and workspace:
       -i 1            wall 15.0 s   (reported compile 10055.8, execute 4016.3 cold)
       -i 1 --warmup   wall 24.5 s   (reported compile  9520.5, execute  344.8 warm)
   The reported compile is unchanged, so the extra ~9.5 s is a second, silent
   planner pass.  Measured end-to-end through the actual booth page over a
   5-cycle soak (medians): base 13.9 s, si 10.2 s, gem 25.2 s, ssrf 24.7 s.
   So a gem/ssrf click is ~25 s of wall clock for a 0.33-0.80 s query, and
   roughly 19 s of that is TWO compiles.  The earlier "~10 s wall" estimate in
   FINAL_GROUPING_LADDER.txt was wrong because it counted the compile once.
   The UI now quotes the measured number ("Compiling plan… ~25 s") instead of
   an estimate.  Fixing G1 fixes most of G1b for free; alternatively the booth
   could run the timed iteration without a separate warmup plan.
G2 THE H-SI HIDDEN CARD'S TIME HALF IS DEAD.  On v6 "GEM without SI" cost 7952.8 ms
   = 9.4x rung2.  On a quiet machine here it is 955.4 ms = 1.20x rung2 (the loaded
   reading, 1.35x, was flattering it).  Part 1 no longer carries the PROFILE_OF join,
   so GEM's split on `a` is not poisoned by the bot graphlets any more.
   Do NOT quote the 9.4x card with this workspace.  Two things do survive and are
   what the booth now says:
     - the MEMORY half of the same card: H-SI's peak is 5,961,518 rows vs rung2's
       167,260 = 36x.  GEM without SI buys back the time but still buffers 36x the
       rows, so SI is what makes peak == answer.
     - the SI RUNG itself, which is untouched: -45.4%, -37.3% worst case.
   The UI what-if has been restated accordingly (title "SI off under GEM — the split
   survives, the buffer does not"), with the 9.4x claim removed and the honest 1.20x
   and 36x in its place; the QA suite asserts the string "7,953" never reappears.
